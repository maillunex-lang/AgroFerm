# D10. Технологии

Статус: `PLANNED`. Наблюдения на 2026-11-11, не решения.

Godot 4.7.2 — последний известный stable. Godot 4.8 на 2026-11-09 был beta 3, stable не объявлен. Это надо перепроверить в день выбора, а не цитировать вечно.

## Q-TECH-001

**Вопрос.** На каком движке фиксируем клиент?

### Вариант A. Godot 4.7.2 stable, GDScript

Патчи 4.7.x принимать. На 4.8 не переходить, пока не выйдет stable и не будет отдельного решения о миграции. Экспорт Android из этой ветки.

- Плюсы: известная ветка, GDScript проще для нескольких ИИ, чем связка C#. Совпадает с постановкой «актуальный stable».
- Минусы: 4.8 с mip-стримингом может быть полезен позже. Его нет как stable сейчас, значит брать нельзя.
- Сложность: 4/10 на пустом проекте, выше на контенте.
- Производительность: Mobile/Compatibility ещё не выбраны. Сам факт 4.7 не гарантирует 30 FPS.
- Развитие: миграция на следующий stable отдельным этапом, не фоном.
- Рекомендация: да.

### Вариант B. Ждать Godot 4.8 stable

- Плюсы: новее рендерер и стриминг текстур, если релиз это сохранит.
- Минусы: дата stable не обещана. Проект стоит. Бета запрещена для фундамента.
- Сложность: 2/10 на ожидании и неизвестно на миграции беты.
- Производительность: выигрыш не измерен на нашей сцене, сцены нет.
- Развитие: простой без пользы.
- Рекомендация: нет. Пересмотреть, когда 4.8 stable выйдет.

### Вариант C. Godot 4.7 с C# вместо GDScript

- Плюсы: один язык ближе к строгому серверу, если кому-то так спокойнее.
- Минусы: экспорт .NET на Android тяжелее, сборки больше, ИИ чаще путает API. Сервер всё равно на Go, общего языка не будет.
- Сложность: 6/10.
- Производительность: размер клиента хуже для цели APK.
- Развитие: не оправдано.
- Рекомендация: нет.

### Вариант D. Другой движок

Unity, Unreal или свой.

- Плюсы: у каждого есть аргумент в вакууме.
- Минусы: постановка называет Godot. Смена движка — другой проект и другие лицензии. Сейчас нет причины.
- Сложность: 10/10 относительно уже принятой рамки.
- Производительность: неизвестно и не повод менять вслепую.
- Развитие: переписывание документов.
- Рекомендация: нет.

**Рекомендация:** A.

## Q-TECH-002

**Вопрос.** Какой рендерер Godot целиться на Android?

### Вариант A. Не фиксировать рендерер до прогона на устройствах

В прототипе выбрать один кандидат, записать имя устройства и кадров. Compatibility (OpenGL 3) и Mobile (Vulkan) сравнить на одной сцене хозяйства. Переключатель в настройках игрока не обещать: смена рендерера может требовать другой сборки или перезапуска, это проверяется, а не декларируется.

- Плюсы: честно. Не врёт про Vulkan. Не запирает проект.
- Минусы: дольше до «окончательной» картинки. Нужны устройства, не только эмулятор.
- Сложность: 6/10 на эксперименте.
- Производительность: смысл вопроса именно в ней. Ответа до таблицы нет.
- Развитие: решение становится `APPROVED` только с таблицей прогона.
- Рекомендация: да.

### Вариант B. Сразу Mobile / Vulkan

- Плюсы: современный путь Godot 4.
- Минусы: на части бюджетных GPU Vulkan капризный. Без списка устройств это лозунг.
- Сложность: 5/10.
- Производительность: может быть лучше или хуже Compatibility. Неизвестно.
- Развитие: отступать к GL после контента больно, если материалы завязаны на Vulkan.
- Рекомендация: нет как слепой выбор. Допустимый кандидат внутри A.

### Вариант C. Сразу Compatibility / OpenGL

- Плюсы: шире класс устройств, проще первый кадр.
- Минусы: часть эффектов Godot 4 слабее или иначе. Можно упереться, если позже нужен Vulkan-only приём.
- Сложность: 4/10.
- Производительность: часто стабильнее на слабых, не всегда. Не измерено.
- Развитие: разумный кандидат внутри A, не догма.
- Рекомендация: нет как слепой выбор. Практичный первый кандидат для прогона.

### Вариант D. Две одновременные сборки Vulkan и OpenGL в релизе

- Плюсы: покрытие парка.
- Минусы: двойной тест всего контента, двойные баги материалов. Дорого для команды из ИИ.
- Сложность: 8/10.
- Производительность: выигрыш есть только если обе сборки живые. Иначе двойная цена.
- Развитие: возможно гораздо позже, не в прототипе.
- Рекомендация: нет сейчас.

**Рекомендация:** A, первым прогоном сравнить C и B на сцене двора.

## Q-TECH-003

**Вопрос.** Какой формат сетевых сообщений?

### Вариант A. JSON по WebSocket для игровой сессии и JSON по HTTPS для входа и админки

Схема сообщения версионируется. Большие бинарные паки карты не идут через этот канал: они качаются файлами.

- Плюсы: читается человеком и ИИ, логируется, быстро отлаживается. Для десятков сессий размера JSON хватает.
- Минусы: многословнее бинарного. Для частого руля может стать шумным. Руль ещё не в первом срезе.
- Сложность: 4/10.
- Производительность: достаточно для цели «десятки сессий». Для толпы рулей пересмотреть отдельно.
- Развитие: бинарный канал можно добавить только для положения машины, не переписывая экономику.
- Рекомендация: да.

### Вариант B. Бинарный протокол с первого дня

- Плюсы: компактнее.
- Минусы: хуже отладка, больше ошибок ИИ, выигрыш не нужен на экономике раз в несколько секунд.
- Сложность: 7/10.
- Производительность: лучше на бумаге, бесполезно без измерения.
- Развитие: преждевременно.
- Рекомендация: нет.

### Вариант C. Только HTTPS, без постоянного сокета

Клиент опрашивает сервер.

- Плюсы: проще инфраструктура.
- Минусы: руль и живой чат мучаются. Либо частый опрос, либо мёртвый UI.
- Сложность: 3/10.
- Производительность: лишние запросы.
- Развитие: сокет всё равно добавят.
- Рекомендация: нет для сессии. HTTPS оставить для входа, админки и паков.

### Вариант D. Свой UDP

- Плюсы: классика шутеров.
- Минусы: нам не шутер. Потеря пакетов для денег недопустима, значит надёжность писать самим.
- Сложность: 9/10.
- Производительность: выигрыш не в той игре.
- Развитие: нет.
- Рекомендация: нет.

**Рекомендация:** A.

## Q-TECH-004

**Вопрос.** Как устроен сервер?

### Вариант A. Один модульный процесс на Go

Модули из предварительной архитектуры. Один бинарник. Общие транзакции PostgreSQL. Не микросервисы.

- Плюсы: один отладчик, одна транзакция на сделку, мало DevOps. Хватает ранней цели нагрузки, пока тесты не скажут иное.
- Минусы: процесс один. Вертикальный потолок есть. Его рано бояться.
- Сложность: 5/10.
- Производительность: лучшее соотношение для стенда 4 vCPU.
- Развитие: модуль можно вынуть позже, если измерение упрётся в конкретный модуль, не «на всякий случай».
- Рекомендация: да.

### Вариант B. Микросервисы по доменам сразу

Рынок, ферма, чат, ИИ отдельно.

- Плюсы: картинка для масштаба.
- Минусы: распределённые транзакции денег. Постановка запрещает усложнять заранее.
- Сложность: 9/10.
- Производительность: накладные расходы съедят маленький VPS.
- Развитие: нет.
- Рекомендация: нет.

### Вариант C. Сервер тоже на Godot

- Плюсы: один язык с клиентом.
- Минусы: хуже как долгий авторитетный экономический процесс, слабее привычные средства миграций и админки. ИИ чаще смешает клиент и сервер в одной сцене.
- Сложность: 7/10.
- Производительность: не выигрыш для PostgreSQL-экономики.
- Развитие: спорное.
- Рекомендация: нет.

### Вариант D. Бессерверный бэкенд

Облачные функции и таблица как сервис.

- Плюсы: меньше своего DevOps в теории.
- Минусы: долгий мир и планировщик плохо лежат на коротких функциях. Транзакции и цена непредсказуемы. Привязка к вендору.
- Сложность: 8/10.
- Производительность: холодные старты против планировщика.
- Развитие: нет для авторитетной симуляции.
- Рекомендация: нет.

**Рекомендация:** A.

## Q-TECH-005

**Вопрос.** Что хранит данные?

### Вариант A. PostgreSQL как единственная база. Деньги и количества — BIGINT

Redis не поднимать, пока конкретный запрос не покажет, что кэш нужен. Файлы паков — объектное хранилище или каталог на диске стенда, не строки в базе. Миграции в репозитории.

- Плюсы: один источник правды, нормальные транзакции, понятные бэкапы. Целые деньги не плавают.
- Минусы: горячие счётчики потом могут попросить кэш. Это потом.
- Сложность: 4/10.
- Производительность: достаточно для ранней цели. Индексы проектируются вместе со срезом, не «на все таблицы мира».
- Развитие: Redis добавляется как ускоритель, не как второй источник денег.
- Рекомендация: да.

### Вариант B. PostgreSQL и Redis сразу

- Плюсы: привычный шаблон MMO-статей.
- Минусы: два места, где может разойтись истина. На пустой игре нечего кэшировать.
- Сложность: 6/10.
- Производительность: не измерена как необходимость.
- Развитие: преждевременно.
- Рекомендация: нет.

### Вариант C. SQLite на сервере

- Плюсы: просто для соло.
- Минусы: один писатель, хуже параллельные сделки рынка. Прототип может, общий мир упрётся.
- Сложность: 3/10.
- Производительность: хороша до первой конкурентной записи.
- Развитие: миграция на PostgreSQL посреди экономики опасна. Лучше начать там.
- Рекомендация: нет. Локальный файл у разработчика допустим только как личный черновик, не как схема проекта.

### Вариант D. Документы без схемы

- Плюсы: быстро накидать сохранение.
- Минусы: деньги без ограничений целостности. Нельзя надёжно запретить минус.
- Сложность: 4/10 на старте, 9/10 на починке.
- Производительность: непредсказуемые документы.
- Развитие: нет.
- Рекомендация: нет.

**Рекомендация:** A.

## Q-TECH-006

**Вопрос.** Как доставляются игровые ресурсы?

### Вариант A. Тонкий APK и версионированные паки

В APK: код, вход, загрузчик, обязательный минимум UI. Остальное качается паками с манифестом, контрольной суммой, докачкой и откатом битого файла. Паки не содержат исполняемый код. Цель размера APK до 95 МБ сохраняется как цель, не как обещание до сборки.

- Плюсы: совпадает с постановкой. Карту и культуры можно обновлять без нового APK, пока протокол совместим.
- Минусы: нужен хостинг паков и экран «не хватает места».
- Сложность: 6/10.
- Производительность: влияет на первый запуск, не на кадр. Кэш обязателен.
- Развитие: штатно.
- Рекомендация: да. На самом первом внутреннем билде допустим один APK без паков, если он и так маленький, с пометкой «временно, не релиз».

### Вариант B. Всё внутри APK всегда

- Плюсы: нет загрузчика.
- Минусы: каждая культура и карта раздувают магазин. Цель 95 МБ умрёт на республике.
- Сложность: 2/10.
- Производительность: установка тяжелее.
- Развитие: упрётся в лимиты площадки.
- Рекомендация: нет для релиза. Терпимо для первого внутреннего APK.

### Вариант C. Ресурсы качаются по файлу с произвольного URL без манифеста

- Плюсы: быстро накидать.
- Минусы: подмена файла, нет целостности, нет версии. Небезопасно.
- Сложность: 3/10.
- Производительность: непредсказуемые докачки.
- Развитие: нет.
- Рекомендация: нет.

### Вариант D. Исполняемый код тоже догружается с сервера

Патчи логики мимо магазина.

- Плюсы: быстрые фиксы.
- Минусы: постановка запрещает. Магазины приложений против скрытого кода. Дыра безопасности.
- Сложность: 7/10.
- Производительность: не важно.
- Развитие: нет.
- Рекомендация: нет.

**Рекомендация:** A.

## Q-TECH-007

**Вопрос.** Где живёт админка?

### Вариант A. Отдельное веб-приложение React + TypeScript к тому же API

Игровой клиент не содержит админских экранов. Роли на сервере. Черновик справочника публикуется командой, не правкой таблицы.

- Плюсы: совпадает с постановкой. Можно открыть с ноутбука. Игровой APK не толстеет от админки.
- Минусы: второй проект. Его легко начать слишком рано и слишком широким.
- Сложность: 6/10 на минимальном наборе экранов среза №1, 9/10 на всех 28 разделах сразу.
- Производительность: не влияет на кадр игры. Обычное веб-приложение.
- Развитие: разделы добавляются вместе с системами, не все сразу.
- Рекомендация: да. В срезе №1 только экраны, без которых нельзя проверить прототип: вход админа, хозяйства, одна культура, журнал, флаг техработ.

### Вариант B. Админка внутри Godot

- Плюсы: один клиент.
- Минусы: неудобно на телефоне и странно на компьютере. Путает права игрока и админа в одном билде.
- Сложность: 7/10.
- Производительность: лишний UI в игре.
- Развитие: нет.
- Рекомендация: нет.

### Вариант C. Сначала только SQL и потом панель

- Плюсы: быстро для автора базы.
- Минусы: постановка запрещает штатно менять критичные таблицы в обход правил. SQL станет привычкой.
- Сложность: 2/10 и высокая цена ошибки.
- Производительность: не влияет.
- Развитие: опасная привычка.
- Рекомендация: нет как интерфейс. Миграции схемы — да, данные мира — нет.

### Вариант D. Готовая low-code панель поверх таблиц

- Плюсы: красиво за день.
- Минусы: прямой доступ к таблицам, слабые бизнес-правила, соблазн править баланс руками.
- Сложность: 3/10 на витрине, дальше борьба с инструментом.
- Производительность: не влияет.
- Развитие: нет.
- Рекомендация: нет.

**Рекомендация:** A, узкий набор экранов в первом срезе.
